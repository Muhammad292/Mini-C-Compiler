1. Executive Summary
--------------------
This project implements a MiniC compiler for a restricted subset of the C language. The compiler covers lexical analysis, syntax analysis (LALR(1) via Bison), semantic analysis (type checking, scope resolution), symbol table management, intermediate code generation (three-address code), and error handling with recovery. The implementation uses Flex and Bison and is written in C.

The deliverables include: source code for each compiler phase, test cases (valid and invalid programs), and documentation describing the design and implementation.

---

2. Project Goals and Scope
--------------------------
Goals:
- Implement scanner, parser, semantic analyzer and symbol table.
- Produce meaningful error messages and recover where possible.
- Generate a readable intermediate representation (TAC).

Language subset (supported features):
- Data types: `int`, `float`, `bool`.
- Statements: declarations, assignments, `input()`/`output()`, expression statements.
- Control structures: `if-else`, `while`, `for`.
- Functions: declaration, parameters, calls, `return`.
- Operators: arithmetic, relational, logical (`&&`, `||`, `!`).

Exclusions (out of scope): pointers, arrays, structs, dynamic memory, complex type system.

4. Lexical Analyzer (Scanner)
-----------------------------
Location: `lexer.l`.

Responsibilities:
- Tokenize identifiers, literals (`INT_CONST`, `FLOAT_CONST`, `BOOL_CONST`).
- Recognize keywords (`int`, `float`, `bool`, `if`, `else`, `while`, `for`, `return`, `input`, `output`).
- Operators and punctuation: `+ - * / == != < <= > >= && || ! = ; , ( ) { }`.
- Skip whitespace and comments (single-line `//`, block `/* ... */`).
- Track line and column numbers for error reporting.

Notes on implementation:
- Uses Flex rules to return token types and semantic values via `yylval`.
- Produces `lex.yy.c` during build.

---

5. Syntax Analyzer (Parser)
---------------------------
Location: `parser.y`.

Parsing strategy:
- LALR(1) parser generated by Bison (table-driven bottom-up parser).
- Grammar defines program structure: declarations, function definitions, statements, and expressions.
- Operator precedence handled with Bison `%left` / `%right` directives.
- Dangling-else conflict resolved by Bison defaults (shift over reduce) — verified and acceptable for this subset.

Key non-terminals (examples):
- `program` → `decl_list`
- `decl` → `type ID ';'` | `func_def`
- `func_def` → `type ID '(' param_list_opt ')' block`
- `stmt` → assignment, `if`, `while`, `for`, `return`, block, etc.
- `expr` → literals, identifiers, binary ops, unary ops, parentheses.

Semantic actions:
- Parser actions call into the symbol table and semantic modules to insert symbols, check types, and trigger ICG emission.

Error recovery:
- Simple panic-mode: use `error` productions (e.g., `stmt: error ';'`) and `yyerror()` increments an error counter and writes to `errors.log`.

6. Symbol Table
----------------
Location: `src/symbols.c`, `src/symbols.h`.

Design:
- Stack-based scope model: each time we enter a function or a new block we `enter_scope()`, and on exit we `exit_scope()`.
- Symbol entries record: `name`, `type`, `kind` (VAR/FUNC/PARAM), `scope_level`, `initialized`.
- Lookup rules: inner-most scope shadows outer scopes. Redeclaration in the same scope is an error.

APIs:
- `insert_symbol(SymbolTable*, name, type, kind)` — insert and report redeclaration.
- `lookup_symbol(SymbolTable*, name)` — find symbol by searching scopes.
- `enter_scope()` / `exit_scope()` — manage scope stack.
- `set_initialized()` / `is_declared()` — utility functions for semantic checks.

7. Semantic Analyzer
--------------------
Location: `src/semantic.c`, `src/semantic.h`.

Responsibilities:
- Type checking for assignments and expressions (`check_assignment`).
- Function return type verification (`check_return_type`).
- Boolean operand verification for `&&`, `||`, and unary `!`.
- Implicit numeric promotion rules (allow `int` → `float`).
- Undeclared identifier detection and reporting.
- Maintain global `error_count` and continue parsing where possible.

Rules summarized:
- Assignments: RHS type must be compatible with LHS; `int` can be promoted to `float`.
- Binary arithmetic: `int`/`float` mix yields `float`; `bool` only for boolean ops.
- Relational operators produce `bool`.

---

8. Intermediate Code Generation (ICG)
-------------------------------------
Location: `src/icg.c`, `src/icg.h`.

Representation: Three-Address Code (TAC). Each generated instruction is a textual line like `t1 = t2 + t3` or `x = t1`.

Features:
- Temporary generation (`t0`, `t1`, ...).
- Expression evaluation pushes temporaries on a stack and `gen_binary_op()` emits code combining top two temps.
- Assignments and constants handled with `gen_assign()`, `gen_const_int()`, `gen_const_float()`.

Output: TAC printed at the end of a successful compilation via `print_icg()`.

---

9. Error Handling & Recovery
----------------------------

Types of errors handled:
- Lexical errors: unknown characters reported with line numbers.
- Syntax errors: Bison `yyerror()` logs and increments `error_count`.
- Semantic errors: undeclared identifiers, type mismatches, redeclarations.

Recovery strategies:
- Panic-mode: parser uses `error` productions for statements (e.g., `stmt: error ';'`), allowing resynchronization at statement boundaries.
- Semantic errors are reported but do not abort the entire compilation unless a threshold of errors is reached.
- All errors are appended to `errors.log` with line number, message, and suggestion where applicable.

12. Design Decisions and Rationale
----------------------------------
- Use of Flex/Bison: Meets course requirement to use automated tools. Bison generates an LALR(1) parser which is robust for C-like grammars.
- LALR(1) vs LL(1): Chosen LALR(1) to rely on Bison; it handles left recursion and yields smaller grammar changes to support real-C constructs.
- Error Recovery: Implemented panic-mode to continue parsing and report multiple errors — useful for test suites and grading.
- Three-Address Code: Chosen as the intermediate representation because it's concise and easy to verify in a lab setting.

13. Limitations and Future Work
--------------------------------
- The type system is small; no structs, arrays, or pointers.
- No optimization passes on TAC.
- Function call codegen is textual TAC only (no stack frame layout or assembly generation).
- Future work: generate x86/ARM assembly, add symbol offsets, implement better short-circuit codegen for logical ops, and extend the type system.
